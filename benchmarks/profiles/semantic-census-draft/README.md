# Diagnostic construction census — unapplied draft

This is source preparation during indexed-storage confirmation2. It has not been applied, compiled, tested, profiled or used to measure workloads. After timing ended, gofmt parsed/formatted the two new Go files, and git apply --check accepted the regenerated patch against the restored source; these are not compilation or test results. Production source and binaries are unchanged. Review and validate after the storage evidence sequence and direct-native milestone; do not run a competing build during timing.

The patch targets preserved saturated source78b76607 at e94bc1f, not the indexed candidate. It adds diagnostic-only code and instrumentation at four actual miss boundaries: declaration signature construction, call signature resolution, class/interface type construction and type instantiation. Existing cache hits and type-instantiation fast exits remain outside the spans. Other query families, relation misses and property synthesis are not covered yet. No new cache or sharing behavior is introduced.

Records include checker owner, raw AST/symbol/type/mapper/alias pointers, request mode, candidate-array/resolving state, flow/instantiation depth, active-mapper count, resolution start, normal/deferred/error completion, nested diagnostic additions and type/instantiation counter deltas. Only existing fields are read; no lazy semantic IDs or additional semantic queries are requested. Pointer identities hold only within one process, not across runs. Source location is metadata, not an equivalence key. Mapper/inference generations and complete mutable contexts are NOT reconstructed. Every record remains unclassified for sharing, including apparently matching origins.

Each checker has a private span stack and a 50,000-record cap. Excess distinct requests go into an explicit unclassified overflow aggregate; overflow nested-key counts do not denote real semantic recursion. `NestedSameRawKeyEntries` only counts overlapping selected spans with identical raw keys; context-changing recursion and early cached observations can be missed. Absence of this counter is not proof of acyclicity. The collector retains pointers and adds allocation/clock/label work, so both memory lifetime and cost are perturbed. It requires the pool's existing exclusive-checker ownership. The global registry is only locked at checker registration and final flush, after ordinary CLI workers have joined. API/LSP/watch/build modes are rejected when enabled; this diagnostic lifecycle is not a project-system implementation.

Enable with a unique `TSC_GO_CENSUS` output path. Optional `TSC_GO_CENSUS_CPU_LABELS=1` adds checker/record/family labels for the existing CPU profiler; this assumes the standalone diagnostic CLI owns goroutine profiling labels. The file is created exclusively after compilation, with a limitations header and one JSON record per checker. Flush failures cause a nonzero diagnostic-tool exit. Instrumented binaries must never enter PERF.md or the normal performance harness.

Inclusive counters must not be summed as disjoint work. Exclusive elapsed time subtracts nested selected spans, but contains scheduling/GC and instrumentation effects and is NOT sampled CPU or a performance forecast. CPU labels alone do not remove profiler/instrumentation distortion. An uninstrumented control and cost attribution excluding recorder frames are required; indirect GC perturbation remains a limitation. The pinned Go runtime documents that spawned goroutines inherit profiling labels. A source search found no direct production `go` statements in the checker package, but transitive spawning is not ruled out: validate it before treating labeled CPU as exclusive to a span. This draft does not satisfy the analysis document's 10% non-overlapping CPU research gate and cannot justify sharing a fact family.
