# Prehashed full-width relation cache: source-only feasibility

A specialized cache is semantically viable and worth an isolated experiment, but the evidence supports a bounded optimization of Sentry's relation-table operations, not a large compiler-wide improvement. The simplest array-of-structs open-address table is unlikely to save memory. A structure-of-arrays design can save some slot padding, with materially worse whole-table growth peaks than Go's current Swiss map. No patch, build, test or profile was produced for this audit.

## Actual contract and coverage

`internal/checker/relater.go:99–115` owns the entire production results-map interface: get, set and size. The five distinct Relation objects initialized in checker.go:1059–1063 are subtype, strict subtype, assignable, comparable and identity. Their pointer identities are semantically significant elsewhere; replace their storage, not the five objects or their identities. Enum relations use a different key/map and are outside this proposal.

There are two result reads (relater.go:220 and3098), and three writes (427,3192,3203). No production iteration, deletion, map-element pointer, public map exposure or map-copy consumer was found. One test directly clears `assignableRelation.results` to nil (primitive_union_test.go:119); it must reset the whole replacement store, including count, or use a private clear helper. Preserve independent caches across all five relations and checker instances. Cache operations themselves do not call semantic code or reenter the checker; get should remain read-only. The checker is not safe for concurrent mutation already, but post-population concurrent reads must not introduce new writes.

CacheHashKey is the complete xxh3.Uint128, two uint64 fields Hi/Lo. Preserve equality of BOTH words, including the all-zero key. Do not repack IDs, add an interner, change serialization, or equate keys merely because their initial bucket/hash fragment matches. Existing full128-bit collisions remain the existing equality behavior; this change must introduce no additional collisions into semantic identity.

RelationComparisonResult is uint32 (relater.go:64); currently used bits are0,1,3,4,5,6. Keep the full uint32 rather than narrowing to a byte or stealing a future flag bit. Missing get returns0, but storing an explicit0 must still increase size exactly once, just as a map does. Overwriting an existing key replaces the full value and does not increase count, including success→failure, reliability and overflow-bit transitions. Occupancy cannot be inferred from key0 or value0. Exact size matters to the complexity budget `(16_000_000-size)/8` at relater.go:422. Keep relationCount decrement behavior at callers unchanged even for replacement writes. Cached failure diagnostic elaboration and overflow replay at3098–3119 depend on precise flags and must remain unchanged.

## Layout: real Swiss-map comparison

Local Go1.26.9 `cmd/compile/internal/reflectdata/map.go:25–65` constructs a group as uint64 controls plus eight `{key;elem}` slots. On amd64 this key is16 bytes/alignment8 and the uint32 value4 bytes, so each slot rounds to24; group payload is200 bytes. At the usual7/8 target load this is about28.57 payload bytes per live entry, excluding table/directory headers, allocator rounding and underfull tables. Runtime maps are already pointer-free for these key/value types. There is no saved GC scanning of Type or Symbol pointers to claim.

An AoS `{key128,value32,occupied}` still rounds to24 bytes per slot, so a75%-loaded table costs32 payload bytes/live entry: worse than the Swiss nominal maximum-load comparison. Putting occupancy in a separate byte costs25/0.75=33.33. A SoA of keys16, values4 and one occupancy bit costs20.125/0.75≈26.83, only about6% less than28.57 in that comparison. At80% it is25.16, about12% less, at the expense of longer probes. These are source-derived payload models, not measured sizes or savings; actual occupancies, rounding, extra allocations and directory overhead matter. Separate slices require three allocations per capacity; a block layout can reduce allocations but adds indexing complexity.

Whole-table doubling temporarily retains old+new capacities, roughly3×old payload, and rehashes every entry synchronously. In contrast Go's runtime limits an individual table to1024 slots and splits tables (`internal/runtime/maps/table.go:19,1162–1208`). This is a serious RSS/pause risk on large Sentry caches. A custom monolithic table could improve total allocated bytes yet regress peak memory or latency. Avoid claiming the289MiB disappears; live keys/results still require storage.

## Minimal bounded design to test later

Keep Relation.results as an optional pointer to a private store, so zero Relation and nil-reset behavior remain simple. Store full key/value arrays, an occupancy bitmap, exact count and optional fallback Go map. Start lazily; use power-of-two capacity and initially75% load. Full-key equality gates every read or replacement. Probe existing entries before growing on an overwrite so repeated replacement never causes unnecessary growth. No deletions/tombstones, eviction, entry references, unsafe packing or shared global storage.

Indexing may consume low prehash bits directly; equality still compares Hi+Lo. Public unseeded xxh3 is not a cryptographic or keyed adversarial guarantee. Merely XORing a per-table seed into the low bucket bits does not change which keys collide, so it is not a flooding defense. Mixing both words with a seed can spread more patterns, but adds work and still needs a bounded policy.

A minimal safe experiment can use direct low bits plus a fixed insertion probe budget (for example64). If an insert or rehash would exceed the budget, permanently convert that relation to the existing Go map, copying all occupied entries including explicit zeros; then discard arrays. This retains the runtime's randomized hash behavior for degenerate distributions without implementing a custom secret hash. Every table-mode entry must have insertion distance below the budget; read may then return0 after an empty slot or the budget, without mutation or looping indefinitely. Equal-low-word/different-high-word keys must never compare equal. On growth, construct a temporary new table and publish only after successful reinsertion; fallback must use the complete OLD contents plus the pending new key, not partially rehashed state. Bound capacity doubling against int/byte overflow and keep at least one empty slot. Do not turn exhaustion into dropped results or an infinite probe.

This adds fallback complexity, but a raw deterministic unbounded linear probe is not an acceptable production replacement for a randomized runtime map when input projects may be untrusted. No need to implement a full Swiss control-byte engine before evidence justifies it. First compare this conservative full-key design, including construction/growth, against the existing map on actual compiler workloads. Reject it if memory peaks or non-Sentry times regress; a custom grouped/splitting design would be a separate larger project.

## Required validation before adoption

Differential randomized operation sequences against map, covering0/all-bit keys and values, repeated replacement, equal bucket bits with distinct full keys, multiple growths, overwrite at threshold, explicit0 size, and fallback during initial insertion AND rehash. Verify nil reset and isolation of all five Relation instances. Concurrent reads after population should pass race checking. Full API regressions must cover cold/warm recursive generic constraints, repeated per-use failures and cached overflow/reliability replay; representation tests alone do not prove diagnostics. Retain upstream full conformance and native parity, then isolated same-input alternating timings with RSS. This audit authorizes none of those executions yet.
