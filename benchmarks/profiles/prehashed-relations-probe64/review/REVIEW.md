## Tests inspected; remaining limits

Seven top-level tests, six explicit subtests (two each for differential, rehash and concurrency) imply13 terminal passing test records if executed successfully. This is a static count, not a pass result.

Coverage is substantive: all-bit values and zero keys; exact count/overwrite/reset; deterministic ordinary/colliding differential writes; growth after six-of-eight entries; last-slot wrap and64/65 collision boundary; both transactional rehash failure branches; original arrays unchanged; post-population concurrent readers; checked arithmetic boundary without huge allocations. The smaller-capacity rehash fixtures correctly exercise old-entry failure with65 inputs and pending-entry failure with64; they do not prove those patterns arise when production doubles.

Remaining worthwhile coverage before acceptance:

1. Public cached overflow/reliability diagnostic replay is not directly covered by these storage tests. Setting flag bits proves their retention, not the actual recursiveTypeRelatedTo error path. Preserve full existing API/conformance/native gates; if a targeted fixture is added, assert repeated source locations/codes against pinned Go semantics, not native alone. No need to weaken scope or bypass diagnostics to obtain a pass.
2. The synthetic array of five Relations proves independent stores, not semantic execution through every real relation kind. Current primitive_union tests and broader checker/conformance validation remain necessary.
3. Nil reset is exercised in table mode only. A small additional fallback-populated reset-and-reinsert case would directly cover reclaiming the permanent map mode. Source logic already appears correct; this is a nonblocking test gap.
4. The probe fallback fixture checks a bounded miss and then conversion but does not explicitly overwrite the distance63 key immediately before conversion. The existing differential/retrieval coverage plus shared find path support the invariant; a boundary overwrite check could strengthen this without changing production design.
5. Race/checkptr execution is still required. The read-only race fixture checks already published tables/maps; it cannot justify concurrent compiler writes or expose every semantic lifecycle path.

## Performance and retention risks

These are actual structural risks, not a prediction of a regression:

- Every small initialized relation gains a cache object plus three arrays; pointer-free map payloads were already not scanning Type/Symbol pointers. No large GC-scanning saving follows from this representation.
- Separate key/value/occupancy accesses and scalar linear probing replace Go Swiss-map control-byte/group operations. Saved second hashing may be outweighed by extra loads, branches, helper calls or poor locality. No assembly/inlining inspection was performed.
- Monolithic growth scans the entire old capacity and keeps old/new arrays simultaneously. Fallback during growth may additionally retain the abandoned destination and the replacement map until GC sees their lifetimes end. Clearing receiver fields does not immediately reclaim heap memory. These costs can matter for large Sentry relations even if cumulative allocation decreases.
- A64-probe threshold may be reached by ordinary large-table clustering, not only malicious same-low-word keys. Permanent fallback can therefore pay custom-table allocation/growth first and map reconstruction later on real workloads. No data currently establishes fallback frequency or mode residency. Timed instrumentation should not be introduced casually; inspect behavior separately if timings/RSS need explanation.
- Checked capacity prevents integer overflow, not memory exhaustion. The custom store cannot inherit Go's bounded individual-table split behavior; do not call its whole-table growth equivalent to runtime map growth.
- The existing pointer profile's Relation.get4.71% Sentry cumulative CPU and Relation.set6.28% sampled allocated bytes are exposure bounds, not removable totals and not current saturated-candidate measurements. Eliminating all get exposure would remove at most that observed CPU fraction; actual implementation must still probe/compare. The custom store cannot establish10× or explain the whole native gap. Do not sum overlapping runtime map/hash samples.

Recommendation: no production correctness blocker found statically, but keep the change isolated, run focused normal/race/checkptr plus full semantic gates after release, and require representative direct Go/Go timing AND RSS evidence before retention. Reject if non-Sentry workloads or peak memory regress enough to outweigh any measured benefit. No broader map conversions or numeric-key changes should be folded into this experiment.
