# Indexed cache for pending instantiated members (candidate)

The pending-member source already freezes a string-to-position layout. This candidate replaces the separate per-instance string-keyed symbol cache with a lazily allocated slice indexed by that layout. The source name map, decision bits, symbol construction order, final-name-wins duplicate handling, materialization and release points remain in place. No cross-checker sharing or extended cache lifetime is introduced.

This is a narrow implementation of the indexed-storage direction in OPTI_ANALYSIS_01.md. It differs from the rejected ValueSymbolLinks handle experiment: positions already exist, so no new identity assignment or handle lookup is required. Costs include a larger pending-member header and full-source-length allocation when a single property is requested; sparse requests on large types may regress memory. The frozen source layout must never be independently reconstructed from map iteration.

Historical normal-profile map call edges are recorded in the two text reports and `selection.json`. The ownMember/memberAt sampled lookup edges are small (Sentry0.08/0.04CPU seconds; VSCode0.16/0.01seconds). ownMember also contains the unchanged source-name map. These edge costs are not a candidate speedup budget or evidence of the 10× target. Allocation and memory effects require end-to-end measurement.
