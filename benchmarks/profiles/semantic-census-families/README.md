# Bounded family-level diagnostic profiles

The archived patch adds `TSC_GO_CENSUS_MODE=families` to the isolated diagnostic compiler. It aggregates the four selected construction/miss families without retaining pointer keys, and reuses spans by nesting depth. At most four records per checker are emitted; this mode deliberately cannot identify repeated keys or equivalent results. Existing detailed mode remains available. Production source and default executable have been restored to the exact saturated baseline.

Preserved diagnostic executable: `packages/tsc-go/dist/tsc-go-semantic-families`; source and build identities are in `source-final.json` and `build-final.json`. `evidence.tar.gz` contains executed controllers, manifests, raw diagnostics, census JSONL, CPU/allocation profiles, decoded profiles and test output. The archive records original absolute execution paths. Extract into a fresh directory. The source snapshots and patch reconstruct the diagnostic implementation against e64135a.

Nine focused top-level tests (11 named passes) pass normally and under race detection. Eight CLI fixture comparisons match diagnostics, status and all six semantic counters with one/four checkers and labels off/on. An initial test-append command used the wrong working directory; it failed before appending tests, then an exploratory test process ran while final tests were being prepared. Only `normal-final` and `race-final` are authoritative for the finalized source. No new full conformance, root-suite, checkptr or native-suite run is claimed for this diagnostic extension.

Each workload has one profiled baseline, one unlabeled family run and one labeled family run at each checker count. Input discovery and physical-file hashes are preserved. These are diagnostic samples, not repeated performance measurements, and they do not enter PERF.md.

TypeORM's first strict controller failed on a four-symbol difference in the four-checker labeled run (461599 baseline, 461595 observed). All other counters and diagnostics matched. Six separate unchanged-baseline runs produced 461593–461597 symbols with identical other counters and diagnostics. The failed run and audit remain intact; baseline variation does not establish the root cause. Subsequent controller v2 explicitly records any symbol-only difference while enforcing other counters, diagnostics and exit status. VS Code and Sentry had no counter differences. Final postcheck validates all inputs and artifacts, and retains precisely this one TypeORM mismatch.

All workload family dumps have zero overflow and all sampled joint checker/record/family label references resolve. Four-checker tagged CPU fractions: tRPC21.25%, TypeORM24.71%, VS Code36.87%, Sentry49.64%. These fractions describe the instrumented profiles, include instrumentation effects and can include inherited labels; they are not estimates of removable work or speedup. Unlabeled background GC is not automatically attributable to these families. Nested creation counters remain inclusive.

Call-signature resolution dominates the tagged samples, but tagged function breakdowns show costs distributed across map lookup, semantic side tables, inference and checking. Ordinary completed call signatures are already cached; flow-dependent and in-progress cases have explicit restrictions. No cross-checker equivalent result or safe shared-cache design follows from these profiles. Next investigation should distinguish storage/lookup cost inside this family from actual repeated context-complete work, using the uninstrumented profiles as controls.
