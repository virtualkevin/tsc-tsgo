# Inline small-key serialization, isolated source draft

This is a credible broader experiment, not a performance result. Patch: small-keybuilder.patch (hash and exact source bases in metadata.json). It is layered on the production source from7437132 after the numeric relation-key experiment was rejected. Ordinary relations continue to use full128-bit keys; no numeric interner or RelationKey representation is included. Main sources remain untouched. The new helper/test files retain their previously formatted bytes; git apply --check against the completed rollback passed; no builds, compiler escape/codegen checks, tests, profiles or benchmarks have run for this draft.

## Library and byte equivalence

The repository pins github.com/zeebo/xxh3 v1.1.0 in go.mod/go.sum. Local inspected sources are `/home/dev/go/pkg/mod/github.com/zeebo/xxh3@v1.1.0/{hasher.go,hash128.go}`.

Hasher embeds accumulator words, counters, a key pointer, a block/stripe buffer and seed. Its measured amd64 representation is1184 bytes in the previous codegen capture. Write and WriteString explicitly never return errors, initialize lazily, then copy/process the supplied bytes; they do not retain caller buffer/string storage. Unseeded Sum128 takes the exact Hash128(h.buf[:h.len]) path when no full block was processed. Empty streams are valid. Large streams preserve the same hash across write boundaries. No seed is used by keyBuilder.

Draft keyBuilder contains128 inline bytes, an int length and an optional *xxh3.Hasher (nominal144 bytes on amd64). Short writes append into the array; hash calls xxh3.Hash128 over exactly the populated prefix. On the first write that does not fit, it allocates a zero streaming Hasher, writes the existing prefix once, then streams the current and all later writes. It never retains the whole long key, pools objects, truncates a hash, shares scratch, or changes key lifetimes. hash remains nonfinal: repeated calls and subsequent writes work on both paths.

Integer fields retain explicit little-endian4/8-byte encoding. int converts through uint64 exactly as the previous hashWrite64, including negative sign extension and32-bit architecture behavior. Strings copy their raw bytes, including NUL/non-UTF8, and retain existing length delimiters. Type IDs remain4 bytes; Symbol/Node IDs remain8. Existing marker bytes, origin tags, aliases, generic normalization, tuple labels, readonly/state flags and ordering are unchanged. No cache lookup, error-return or cache-insertion logic changes.

## Complete caller audit

Production keyBuilder creations found in checker.go: type-list, alias, union, intersection, tuple, type-instantiation, indexed-access, template, conditional, ordinary/generic relation, node-list keys; active-mapper instantiation and template-literal instantiation. flow.go1637 additionally builds flow-reference keys.

All builders are local variables. Recursive generic constraint lookup can run another key builder while the outer one is live; each has its own array/overflow hasher. writeFlowCacheKey passes one builder recursively down the same serialization. In the current implementation a false result occurs before any bytes are written: unknown/unsupported leaves return immediately, and recursive failures propagate before suffix writes. Therefore a discarded failed flow key does not currently allocate overflow storage. Resolver calls made while determining validity can still have side effects; their order is unchanged.

No production builder is copied after use, returned by value, stored in a map, captured for later reuse, or used concurrently. The draft explicitly prohibits copying a builder after its first write because copying an overflow pointer would alias streaming state, unlike the old embedded value. This private representation restriction is satisfied by all current call sites; it must remain documented for future changes. Independent nested instances are tested.

Lazy ast.GetSymbolId/GetNodeId calls remain at the original writeSymbol/writeNode sites. They are not deferred until hash(). Current flow-reference failure paths return before these builder ID writes, as described above; resolver side effects during validity checks are preserved. Constraint/type-argument resolution order and diagnostic effects remain unchanged. No new early return surrounds those operations.

Direct old b.h users: its primitive writers, indexed-access accessFlags, and ordinary/generic relation intersectionState. The representation-specific relation_keys_test.go was removed on rollback and has no hunk in this patch. All production sites are converted to the equivalent uint32/uint64 writer. The unused generic hashWrite32/hashWrite64 helpers are removed. New tests independently compare against the library streaming hasher without calling builder serialization methods to construct the expected bytes. There are no other production accesses to keyBuilder's old hasher field.

## Exposure, alternatives and costs

Fresh committed pointer-current Sentry sampled CPU: Hasher.updateString flat1.11%/cumulative1.43%, Hash128 worker flat0.28%/cumulative0.34%, Sum128 flat0.11%/cumulative0.45%, hashWrite32 flat0.11%/cumulative1.04%. VS Code updateString flat0.41%/cumulative0.60%, Hash128 worker flat0.16%/cumulative0.22%. These overlap through calls and are not additive removable costs. Hash128 is still required after buffering. Hasher zeroing is charged to caller instructions and was directly observed in the earlier getRelationKey codegen; the available profiles do not isolate its total cost. The numeric relation-key experiment was rejected after its mixed elapsed results, so ordinary relations still build the full hash and remain in scope. The pointer-current profiles match that key representation; they still do not isolate total zeroing cost or predict savings.

Common shapes are small: a type plus absent alias is5 bytes; an indexed-access key with absent alias is13 (4+4+4+1), or29+4*m for an alias with m type arguments; type-list with absent alias9+4*n; nonempty alias adds its marker, Symbol ID, argument count and IDs.128 bytes accommodates29 type IDs with absent alias, but large unions, generic trees, tuples and template/flow strings can overflow. This is a plausible allocation-avoiding common path, not evidence of the workload's short-key fraction.

The long path introduces a fresh heap Hasher (1184 bytes nominal, allocator class overhead extra) where the previous local embedded hasher could stay on stack. It also recopies the inline prefix once. The Hasher has a key pointer, so it is not entirely pointer-free heap storage. Frequent spills could worsen GC and erase savings. The new writer/stream methods may affect inlining and escape analysis: a slice of the inline array passes to Hash128 and to overflow.Write; those library implementations do not retain input, but actual Go escape/codegen must verify that this does not move every builder to heap. Do not infer nonescaping status solely from source semantics. The array also has stack-zero cost;144 is a source-layout fact, not yet a measured frame.

A growable []byte buffer would add potentially unbounded whole-key retention until hash and multiple growth allocations, so is not used. Global pools/shared checker buffers would add lifetime/reentrancy problems, so are excluded. Separate fixed-format helpers for just5-byte active-mapper or13-byte indexed-access keys with absent aliases would avoid overflow risk and be a smaller fallback experiment if this broad draft spills too often, but would duplicate serialization paths. No such second implementation is included.

## Unrun regression tests

Six new tests cover: byte/string chunkings across lengths0 through4097, exact127/128/129 and xxh3 block/stripe/short-input boundaries; empty writes and repeated hash followed by further writes; explicit little-endian signed/int/type/node/symbol encoding; immediate lazy-ID order; nil/non-nil aliases and zero/nonzero/overflow argument counts; independent nested short/long builders; embedded NUL and text-boundary distinctions in real template keys. The streaming oracle serializes expected bytes independently and checks full128-bit output against both xxh3 streaming and one-shot hashing.
