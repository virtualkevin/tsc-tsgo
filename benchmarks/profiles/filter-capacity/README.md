# One-pass Filter capacity planning candidate

The retained normal-flag allocation profiles identify repeated slice growth inside core.Filter:1,145,505estimated append-line allocations on Sentry and228,473on VSCode. This is sampled cumulative allocation evidence, not a CPU-removal budget or10× forecast. Exact line/caller decodes and hashes are in the sibling filter-allocation-audit directory.

After the first rejected element, this candidate snapshots a nonempty accepted prefix into storage sized for the maximum possible surviving result. With an empty prefix, it preserves the empty view and waits for the first retained tail element before allocating for the remaining tail. This removes repeated growth while keeping a single forward predicate evaluation per element. FilterIndex is unchanged.

The changed allocation policy preserves nil/empty input behavior, original slice reuse when every element is accepted, prefix snapshot timing, callback order/count, and separation of a nonempty filtered result from the input. Empty all-rejected output retains the old nonnil zero-capacity view semantics. Output capacity can differ; sparse results after an early retained element may reserve substantially more storage and retain more memory. No workload memory improvement is assumed.
