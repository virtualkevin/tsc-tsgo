# Three node-key side tables: candidate investigation

The current uninstrumented four-checker CPU profiles assign roughly5% of VSCode CPU to builtin-map paths called by SymbolNodeLinks, SignatureLinks and TypeNodeLinks. The selected fraction is smaller on the other workloads. This motivates testing the existing typed PointerLinkStore for precisely these three tables. It does not predict end-to-end improvement or the10× native target.

This is distinct from the rejected indexed-symbol pilot: no AST layout/allocation handles or indexed arrays are introduced. Key identity, checker ownership and arena value lifetime stay the same. The existing pointer store assumes a non-moving Go heap and preserves typed key/value GC roots. Candidate production delta is three field types; an added actual-checker test checks AST keys/payload graphs across table growth/GC and independent checker ownership.

`analyze.py` attributes each baseline CPU sample containing builtin-map frames to its nearest project caller exactly once. It counts the entire sampled map path, including callees such as allocation/hash functions; it is not isolated lookup latency. Raw profiles are archived in the preceding semantic-census-families evidence. Input hashes and example stacks are in report.json. Initial parser output is preserved; the corrected parser handles pprof generic function suffixes and parses every sampled location. Its totals conserve assigned map-path CPU. These are single profiles, not new timings.

Eight focused tests pass normally, under race detection and strict checkptr; the ten-package root suite passes2339named/115top-level tests, zero skips/failures. Full conformance/native validation and workload measurements remain pending.
