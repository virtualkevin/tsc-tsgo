# Alias-wrapper reuse: source-only feasibility audit

Verdict: duplicate wrapper identities are real by construction, but this audit does not establish a safe broad canonical identity or success-only relation cache. Do not implement alias-erasing interning or general relation reuse from these findings. The useful next step is an untimed, observational duplicate-work census, not a speculative cache. No workload coverage or speedup is claimed.

Reviewed repository HEAD `1633f6ac66404bad0f2d4bed42de02f8e7cda400`. Only source reads and this /tmp report were performed during the parent's quiet window. No Go commands, builds, tests, profiles, compiler runs, or main edits. Local Go and native TypeScript implementation sources are the primary evidence; this is not a claim that their representations are identical.

## Why a large gain is not established

1. `instantiateTypeWithAlias` returns immediately when the input cannot contain type variables and its existing alias arguments cannot contain them. Truly closed, non-generic wrappers therefore often perform no recursive instantiation at all. The `Brand<T> = number & {}` comment explicitly explains why closed constituents with variable alias arguments are different: the alias must still be instantiated so scoped parameters do not leak into declarations. A census must distinguish those cases.
2. Same-constituent union-to-union checks already have a positional shortcut: relater.go2990 `eachTypeRelatedToType` tries matching corresponding members, and `isRelatedToEx` returns immediately for identical pointers before normalization. Equal constituent vectors therefore often cost O(n) identity checks, not an n-by-n structural traversal. Membership and preserved-origin shortcuts avoid more work. The common small-union path deliberately skips the relation cache.
3. Differences between structurally similar constituents are outside the safe hypothesis. Two independently declared object literals are not the same constituent identity; recursively hashing their apparent shapes would be a different, much riskier optimization. Brand symbols, private/protected declarations, enum identity, unique symbols, freshness and call signatures must not be merged.
4. Intersection wrappers own lazy reduction, apparent type, property and structured-member state (types.go1132-1162). Duplicate wrappers can repeat such work, but measuring wrapper counts alone cannot say how much of that state was ever computed. Some expensive lazy work could be duplicated even when relation queries are cheap; that needs separate counts.

## Semantic barriers

**Presentation and construction.** Nodebuilderimpl.go3332 preserves accessible alias names/type arguments; checker.go23505 deliberately avoids inaccessible local aliases and preserves exported aliases for reserialization. Returning a canonical Type in place of an alias-bearing wrapper would change public type identity/display/declaration behavior. Reusing an underlying payload would need an independent design: wrapper-local mutable fields, parent links and alias-sensitive consumers cannot simply be pointed at an existing wrapper.

**Closed is not non-recursive or fully evaluated.** `couldContainTypeVariables` is an instantiation predicate, not a proof of acyclic structure or absent lazy errors. A closed alias such as `type R = string | (() => R)` can recurse. Determining transitive closure by forcing member types, constraints, returns, or conditional types could itself trigger the lazy work/diagnostics the proposed cache is supposed to avoid. Cached false for this predicate is insufficient to certify safety.

**Origins, normalization and checking order.** relater.go2673 normalizes before relation caching; checker.go27906 calls reduction and may normalize intersections; checker.go21716 can resolve never-producing discriminant/private properties. relater.go2912/2918 uses preserved origins and alias identity for existing proven shortcuts. Do not move a new shortcut before normalization, excess-property checks, or weak/common-property checks. Origin and normalization eligibility must be distinguished even if final constituent pointers match.

**Success is not a proof without assumptions.** relater.go3178-3205 promotes root `TernaryMaybe` to `RelationComparisonResultSucceeded` and can mark a batch of maybe-stack keys successful. The stored success bit does not distinguish direct True from discharged recursive assumptions or expanding-depth heuristics. It also stores Unmeasurable/Unreliable variance effects that hits propagate. A new cache cannot treat any existing Succeeded entry as an independently proven alias-free theorem. Even a returned True would need to establish it did not depend on earlier assumption-derived cached successes.

**Stack and budget effects.** maybeKeysSet, constrained broadest-equivalent keys, source/target stacks and recursion identities are separate from completed relation entries. Relater.go818 counts matching recursion identities in TypeId order. Changing those identities changes termination heuristics. relationCount is initialized from relation-map size and decremented on insertions; depth and complexity overflow have diagnostic behavior. A reuse table must not silently replace stack keys, mutate the existing accounting model, suppress overflow failures, or ignore `r.overflow`.

**Relations and diagnostics remain distinct.** Any hypothetical side identity must include relation kind, source/target orientation (except identity's existing symmetry), intersection state, and conservative eligibility. Failures must continue elaborating at each use site with the original aliases; success-only storage avoids copying failure messages but still does not prevent lazy diagnostic effects from being skipped. Object/conditional alias variance fast paths (relater.go3422) are explicitly restricted by type kind and same alias symbol, so expanding the scheme beyond union/intersection roots is unsupported.

## A bounded safe island, not a recommended implementation

After existing normalization/checks, two origin-free union wrappers whose equal-length lists contain the exact same already-regular, non-enum primitive/literal singleton pointers admit a simple finite identity proof for their members. Keep original wrappers and aliases; no recursive/member/constraint traversal is needed for that proof. Exclude error/wildcard/missing/fresh and instantiable forms rather than broadening by structural similarity. This only suggests an equality fast path, not arbitrary reuse of their relation results against a third structured type, and the current positional identity path already handles the same work. It does not justify an added canonical map without measured traffic. General intersections and recursively reachable object members do not fit this bounded proof.

## Future untimed counter plan (not executed)

Collect with a diagnostic-only instrumented binary and fixed source/workload hashes, first single checker then the actual default checker configuration. Keep worker IDs and checker lifetimes separate: TypeIds and mapper identities are not global semantic IDs. No elapsed-time inference from instrumented runs.

1. At actual union/intersection creation/cache miss, group wrapper IDs by a shadow signature of kind plus exact existing constituent IDs **in order**, origin category/identity, and relevant construction flags; record alias variants separately. Also report a looser constituents-only group as an upper bound, never as safe eligibility. Use exact vector comparison behind any hash. Read existing IDs/fields only: do not allocate symbol/node IDs, call constraint/member resolution, or invoke a new couldContainTypeVariables query. Cap retained shadow data and report truncation; histogram counts can be kept without per-file logs.
2. At `instantiateTypeWithAlias`, count early closed/no-mapper exits, actual active-cache misses, and union/intersection worker entries. Group only within the same actual active mapper lifetime. Separate source-alias differences from requested-output-alias differences, and alias-argument type variables from closed constituents. Record constituent instantiate calls and persistent factory/alias-cache hits so duplicate wrapper counts are not mistaken for repeated deep instantiation.
3. At the existing normalized recursive-relation lookup, count real key misses versus hypothetical same-vector-pair hits, split by relation, intersection state, origin eligibility, primitive-only versus opaque object members, and reportErrors. Also count the small-union bypass and existing positional/origin shortcuts: otherwise coverage denominators are wrong. Shadow hits must still run the original relation and verify results; they never return early.
4. Track direct True / False / Unknown / Maybe, stack assumptions, expanding-depth shortcuts, overflow, reliability flags and promotions separately when publishing relations. Existing stored Succeeded alone cannot recover this provenance. Track when a computation reads an assumption-derived existing success; conservative taint propagates to the shadow eligibility result.
5. Count actual member-resolution, reduction, property synthesis and instantiation events under candidate duplicate computations. Attribute exclusive work (or use an explicit event stack) so nested inclusive totals are not summed. Report duplicated work as an upper bound, because side effects may still be required. Count diagnostic additions and cold/warm behavior, while noting unchanged diagnostics alone cannot certify an unevaluated branch safe.
6. Stop if safe-candidate misses are rare or already terminate via member identity/cache hits. Only material exclusive work in a precisely bounded class would justify a separate correctness proposal. Required future tests would cover alias display/emission/accessibility, cold/warm errors and exact positions, recursive closed aliases, mutually recursive generics, deferred constraints, private/unique brands, overload order, variance markers, and depth/complexity boundaries; the pinned conformance suite alone is not a proof of this cache equivalence.

No patch is proposed. This audit rejects broad alias erasure and general success-only reuse at present; it leaves an observational route to quantify whether there is a narrower worthwhile opportunity.
