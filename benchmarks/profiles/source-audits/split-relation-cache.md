# Split ordinary/generic relation caches: source-only feasibility

A lossless split design is feasible and eliminates the prior fallback interner completely. It is a different tradeoff from both the archived numeric-key experiment and the current512-probe full-width storage experiment. The conservative version uses an explicit24-byte tagged key through recursion tracking, a normal Go map[uint64] result store for ordinary keys, and a normal Go map[CacheHashKey] result store for generic/exceptional keys. It should remain a separate experiment; no implementation, build, test, profile or workload was performed for this audit, and main is unchanged.

## What earlier evidence does and does not show

The archived numeric implementation is `/tmp/tsc-relation-keys-current/draft/packages/tsc-go/internal/checker/{checker,relater}.go`; its source review is `/tmp/tsc-relation-keys-current/AUDIT.md`. It packed ordinary IDs/state, but every generic/exceptional query constructed its complete old128-bit hash, looked that hash up in a checker-lifetime interner, then used the resulting64-bit ID for result lookup and maybe-set tracking. Probe-only generic keys became retained interner entries even if no comparison result was cached. Removing that intermediate lookup/storage has a concrete mechanism, but the old A/B does not isolate its causal cost.

NOTES.md109–110 records candidate ratios1.008 TypeORM,1.046 tRPC,1.001 VSCode,.981 Sentry versus pointer; Sentry paired median.943, with a concurrent ncdu observation whose exact overlap is unknown. It was correctly rejected as a mixed/no-benefit experiment, not proven to regress solely because of interning. Its codegen evidence (ordinary helper frame1240→48 bytes, fast64 map calls) also predates today's saturated128-byte buffered hash builder. The current ordinary relation key hashes only13 serialized bytes with one-shot xxh3; the old1184-byte streaming-hasher clearing advantage no longer applies. Any future packed-key gain must be measured against the current accepted baseline.

## Minimal representation and storage

Use a dedicated comparable value with two uint64 payload words and an explicit kind byte, for example conceptually `{lo uint64; hi uint64; kind uint8}`. On current amd64 its field layout rounds to24 bytes. Constructors must canonicalize all represented fields: ordinary kind stores packed uint64 in lo and sets hi=0; hashed kind stores both original hash words. Kind participates in equality. Do not create an interface/boxed heap object per key, pointer-tag payloads, overwrite a hash bit, truncate the hash, or reserve a possible full128 hash as a sentinel. A separate ordinary domain plus every128-bit hash cannot be injected into an unchanged128-bit representation without additional state; explicit tagging accounts for that information.

Ordinary admission should initially match the already reviewed numeric port: after identity sorting and generic classification, IDs in[1,2^30), state in[0,3], pack `(uint64(source.id)<<32)|(uint64(target.id)<<2)|uint64(state)`. Source occupies bits32..61, target2..31, state0..1. Zero/oversized IDs, unknown future uint32 state bits and all generic references use the ORIGINAL full hash serialization. There is no benefit in broadening the proven range for this first experiment. Ordinary ignoreConstraints remains ignored as before.

Relation.results can remain an optional pointer to a private split store with two lazily initialized maps: ordinary map[uint64]RelationComparisonResult and hashed map[CacheHashKey]RelationComparisonResult. Dispatch get/set on kind, without interning or shared registry. size must return len(ordinary)+len(hashed), so explicit zero results count and replacement does not. nil get/size and assigning results=nil preserve current contracts. All32 result bits remain intact. One optional object preserves the current nil-reset test while adding a small per-active-relation allocation; inline maps inside Relation would require a deliberate reset-interface change and should not be silently substituted.

Use Go maps for BOTH stores in this first design, rather than combining it with the unmeasured512-probe table. That retains randomized map hashing and table splitting, avoids another growth/probe policy, and isolates packed-key routing from storage specialization. If512 later proves worthwhile, its relationship to this alternative requires a separate explicit design/measurement decision.

Current checker.go17489 creates keys. Preserve append order, maybeStart indices, partial discard/commit behavior, maybeCount/source/target recursion limits, and caller relationCount decrements. Never recompute keys on reset: generic resolution may have changed and ordering effects cannot be replayed safely.

`putRelater` at2628 clears the set and pools its backing allocation plus the stack capacity. Thus extra tagged-key/set capacity persists across checks on the free-relater list, although scalar keys retain no Types/Symbols. Both result maps remain checker-owned; do not share them across checker-local Type IDs. size drives `(16_000_000-size)/8` at relater.go422, so summing exact map lengths is essential. Flags consumed in cached failure elaboration, stack/complexity overflow replay, and reliability propagation at3098 onward stay unchanged. Separate domains can avoid a theoretical ordinary-vs-generic old128 hash collision; they must introduce no new equivalence or reduced-width collision. Generic-generic collisions retain exactly the existing hash semantics; no native-style exact token equality claim is added.

## Evaluation ordering, identity and reentrancy

- Identity pairs sort source/target IDs FIRST exactly as getRelationKey currently does. Intersection state does not swap; preserve that behavior.
- Keep `isTypeReferenceWithGenericArguments(source) && isTypeReferenceWithGenericArguments(target)` left-to-right and short-circuit. Its getTypeArguments calls can resolve state. Packing based only on object flags or eagerly probing target would change behavior.
- Ordinary writeType at checker.go17306 only serializes an already assigned uint32 Type ID. It does not perform lazy Symbol/Node ID allocation. Skipping ordinary byte serialization therefore changes no ID-assignment timing; generic detection still must execute. Do not generalize this proof to writeSymbol/writeNode, which do allocate IDs lazily.
- Generic path retains the existing 'g' prefix, shared source/target type-parameter-position sequence, separators, depth<4 recursion, constraint calls, full fallback argument/target IDs and final uint32 intersection state. Exceptional ordinary path retains 's' plus complete IDs/state. Do not import native token spelling.
- Hash builder, constrained flag and tagged return value remain local across getConstraint/getTypeArguments recursion. The split design requires no mutable checker scratch or interner. Returning the value cannot publish a partially constructed key. Broadest-equivalent ignoreConstraints keys retain their original normalization and domain.
- Go maps permit concurrent post-population readers but not checker mutation/read races. No new synchronization guarantees are implied. Key objects are scalar comparable values and add no retained semantic object graph.

## Concrete memory and CPU tradeoffs

Current Go1.26.9 map layout source `/tmp/tsc-toolchains/go/src/cmd/compile/internal/reflectdata/map.go` uses8 controls bytes plus8 aligned key/value slots per group. For nominal amd64 payloads, before allocator rounding and occupancy:

| Storage | Current saturated full128 | Proposed split |
| --- | ---: | ---: |
| Ordinary relation result slot |24 bytes (16 key +4 result +padding)|16 bytes (8 key +4 result +padding)|
| Ordinary result group |200 bytes|136 bytes|
| Generic/exceptional result slot/group |24/200 bytes|24/200 bytes, unchanged|
| maybeKeys element |16 bytes|24 bytes (+50%)|
| Single maybeKeysSet slot/group |24/200 bytes|32/264 bytes (+32% group payload)|

The set calculation includes Go's trailing zero-sized struct-field padding: map slots contain `{key; elem struct{}}`, and compiler `types/size.go:510` adds one byte before final alignment. Thus a16-byte key becomes a24-byte set slot, and a24-byte tagged key becomes32; omitting this rule would understate both payloads. These source-derived sizes have not been checked through an executable layout probe.

The prior numeric draft used8-byte stack/set keys, so this tagged key is3× that draft's stack element and increases its set payload more. Unlike the numeric draft, there is no added full128→64 interner or probe-only lifetime retention. Relative to current saturated code, potential result savings are roughly8 bytes per ordinary occupied-capacity slot, offset by roughly8 extra bytes per tagged recursion-set capacity slot plus8 per stack capacity element, extra maps/store headers and fragmentation. This is layout arithmetic, not a peak-RSS or allocation prediction. Result caches may greatly outlive active recursion, but pooled sets/stacks retain maximum capacity; actual ordinary/generic ratio and retained capacities are unknown.

A map keyed by the tagged24-byte structure will not use mapaccess_fast64; generic composite-key hashing/equality adds work to maybe-set Add/Has/Delete, including ordinary comparisons. A result map[uint64] can use fast64, but whether wrappers inline, the larger key return/copies spill, or routing branches cost more requires later assembly and workload evidence. Do not put the tagged key itself into a single result map: a24-byte key plus4-byte result rounds to32 bytes per slot, losing the intended result-storage saving.

An alternative split maybe-set (ordinary uint64 set plus hashed128 set) would avoid24-byte set hashing and generic-set enlargement, leaving only the ordered tagged stack wider. It requires correctly clearing both sets during pooling and dispatching both constrained and normal probes/delete paths; preserve one shared ordered stack for suffix commits. This is feasible and likely worth considering if a draft is authorized, but increases the scope. Do not introduce parallel stack arrays or an auxiliary key interner merely to hide width without evidence. The simplest correctness baseline is one tagged set; the likely performance baseline may be split sets. Choose explicitly before implementation, rather than stacking variants until a favorable result appears.

## Exposure bound and recommendation

Committed pointer-current Sentry sampled CPU: getRelationKey2.22s/1.80%, Relation.get5.82s/4.71%; Relation.set sampled allocated bytes289.38MiB/6.28%. Other workload relation allocation exposure is smaller (TypeORM1.01%, VSCode.72%; missing tRPC top300 entry is not zero). These are older pointer profiles, not current saturated/512 measurements. Inclusive entries can overlap through reentrant semantic work, so do not sum them or add broad map/hash totals. Ordinary packing removes only part of key construction, result maps still hash/probe, and the tagged recursion machinery adds work. Even removing the entire observed1.80% key-helper CPU is a small component bound, not a wall-time prediction. The map exposure is not all removable; no10× inference is supported.

Recommendation: feasible as a separate later candidate if current512 storage evidence leaves a reason to investigate. Prefer an explicit lossless tagged key, direct ordinary/generic result maps and unchanged generic hash semantics; decide whether transient membership also splits before coding. First retain boundary-domain, generic alpha-equivalence/constraint-reentry, four-call-site, size/flags, partial maybe-stack/pooling, five-relation isolation and repeated diagnostic-position tests. Require generic/full-hash cases whose payload overlaps an ordinary packed key, explicit zero/fullbit hashes, unknown states/oversized IDs, and no extra allocation on read-only generic probes. Full semantic/race/native gates and representative saturated-baseline A/B with RSS remain mandatory before adoption. Current audit authorizes no implementation or execution.
