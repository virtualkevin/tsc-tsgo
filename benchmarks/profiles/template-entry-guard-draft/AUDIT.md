# Finite string-source template relation entry guard (UNRUN)

Prepared only under /tmp. No Go commands, formatting, apply check, builds, tests, profiles, workload runs or main edits. The patch contains one guarded addition to isTypeRelatedTo and two test files. No cache representation change is included. The relater.go source snapshot currently includes the separately managed prehashed cache, but the unified diff contains only the entry guard: it can be rebased on either cache representation or either buffered keybuilder verdict.

Native primary reference: commit44b5440, current packages/tsc-ts/src/compiler/relations.ts452-472. The native change covers finite string and template sources. This draft deliberately takes only the finite string-source case, preserving the full path for every template-source input rather than adding a closure/type-variable predicate.

Proof boundary: after existing fresh-literal normalization and pointer identity, source must have StringLiteral and target TemplateLiteral. The exact fixed start/end/overlap predicate is copied from Go's existing inferFromLiteralPartsToTemplateLiteral (relater.go2446), using the same Go string representation and byte-length operations. A single string source has lastSourceIndex==0 there. Failing this condition yields no placeholder inference and cannot match, under any of the five relations. Passing the predicate makes no decision and executes the old path, preserving number/string/infer-placeholder checks. No symbols, IDs, aliases, constraints or mapper state are read or changed by the guard. Existing strings import suffices.

The API entry is the non-diagnostic boolean isTypeRelatedTo. The diagnostic checkTypeRelatedTo path remains unchanged and can still generate each use-site error. Template sources remain excluded because their full relation can call reportUnreliableMapper even on disjoint text. The broader native template-source clause avoids that shortcut when placeholders could contain type variables; this draft avoids the clause entirely. It does not modify relation budgets, recursion keys, or cached failure bit semantics, though skipped finite failures naturally stop adding entries as with other existing primitive entry shortcuts.

Prepared tests:

- TestStringTemplateEntryGuardMatchesFullRelater: 12 finite-text cases × five relation kinds × regular/fresh literals =120 subtests. Cases include mismatch at either end, forbidden prefix/suffix overlap, empty input, empty interpolation, Unicode and NUL. Each runs the entry then clears the relation store before independently calling checkTypeRelatedTo, which bypasses the new top-level guard. Explicit expected booleans supplement the shared engine oracle. For disjoint texts it asserts no relater/cache was created, so this optimization-path assertion intentionally does not pass the unoptimized baseline. Existing reliability flags must be identical after both paths.
- TestStringTemplateEntryGuardPreservesTemplateVarianceReporting: a template source with a real marker type and disjoint fixed prefix must still execute reportUnreliableMapper and propagate its flag. Uses a real reporting mapper callback, not nil. This tests the production exclusion rather than mocking the result.
- TestStringTemplateEntryGuardRepeatedDiagnostics: actual parsed API fixture warms the boolean failed query, then requires exactly two TS2322 errors at two distinct assignment positions across repeated diagnostic queries. Valid adjacent statements assert inference into a template placeholder and a deferred generic template source remain intact. Uses existing pendingAPIChecker and the same exact-position method as retained relation API regressions; raw checker diagnostics do not use expect-error directives.
